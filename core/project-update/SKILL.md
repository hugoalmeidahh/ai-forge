# Project update

Choose the requested audience and existing team format. Read the actual card, diff, test evidence or incident timeline before asserting completion. Drafting an update does not authorize sending it.

## Choose the structure

- Status: outcome/progress → evidence → risks/blockers → next action with owner/date when known.
- Incident: user impact and current state → verified timeline → mitigation → unresolved cause → follow-up. Separate hypothesis from confirmed cause.
- Leadership/decision: decision needed → recommendation → alternatives/trade-offs → consequences and deadline if real.
- FAQ/release: reader question → concrete answer → scope/version → source or next step.

Avoid vanity activity lists, invented percentages, unsupported ETAs and claiming a green build from an earlier commit. Keep sensitive customer details out of broad updates. Report failed/not run separately from passed. Link the actual artifact or commit where available; do not fabricate IDs.
